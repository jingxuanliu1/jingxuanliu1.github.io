01 / Problem and motivation

Per-request inference leaves useful capacity on the table.

With small CPU inference work, scheduling overhead becomes visible. Executing every request independently can underuse vectorized computation, while waiting too long to build a batch can make latency worse. The gateway also has to remain predictable when callers time out, queues fill, or a preferred backend is unavailable.

Engineering question: how much can a transparent, bounded scheduler improve the same workload—and can the claim be reproduced with the machine, seed, request count, concurrency, and error count recorded?

02 / Project scope

A focused request path, not a production serving platform.

FluxServe implements a local HTTP and Python-callable inference gateway around a deterministic 128-to-1 linear projection. The scope is deliberately narrow enough to inspect the scheduler and measure its behavior.

  • Versioned model registry and typed backend contract.
  • Python reference, NumPy FP32, NumPy FP16, and symmetric NumPy INT8 backends.
  • Optional ONNX Runtime and PyTorch adapters that report unavailable rather than pretending to execute.
  • Configurable queue capacity, batch size, wait budget, worker count, deadline, cache TTL, and cache capacity.
  • Health, readiness, registry, inference, cancellation, and Prometheus-format metrics endpoints.

03 / My contribution

I built the scheduler and the evidence around it.

I implemented the admission path, deadline-prioritized queue, dynamic batch scheduler, cache-key rules, backend resolution, cancellation paths, latency instrumentation, HTTP surface, tests, and benchmark harness. I also documented failure modes and separated executed backends from optional adapters.

This was not an integration of Triton or vLLM. The scheduler is intentionally implemented directly with an asyncio condition and explicit queue so its ordering, wait budget, backpressure, and completion semantics remain inspectable.

04 / Architecture

The request path keeps policy explicit.

05 / Important engineering decisions

Dependability comes from constraints.

Deadline before arrival order

Requests sort by absolute deadline and then sequence. A batch never waits beyond the earliest selected request’s remaining slack.

Bound every queue and wait

Admission rejects a full queue, queued work can expire, and batch formation respects both maximum size and maximum wait. Work cannot grow without an explicit limit.

Make cache identity complete

The opt-in TTL/LRU cache hashes model, version, backend preference, and full finite input, preventing cross-version reuse.

Fallback only to a backend that reports ready

Optional ONNX and PyTorch adapters expose why they are unavailable. A request may follow an explicit fallback order without mislabeling NumPy work as another backend.

Move synchronous compute off the event loop

Backend computation runs in a worker thread so admission, timeout, and cancellation handling can continue.

06 / Technical challenges

A fast result is not enough if completion semantics are wrong.

  • Cancellation races: a caller may abandon work while it is queued or while a batch is executing. Workers check whether futures are already completed or cancelled before publishing results.
  • Mixed backend/model work: only requests with matching model, version, and backend resolution keys may share a batch.
  • Backend failure isolation: an exception fails the affected batch and increments failure metrics instead of corrupting unrelated requests.
  • Measurement resolution: the harness moved to perf_counter_ns after monotonic clock quantization was detected.

09 / Limitations

The boundary of the claim matters as much as the number.

  • The verified model is a compact deterministic linear projection selected to expose scheduler behavior, not a deep neural network.
  • ONNX Runtime and PyTorch adapters exist but were not installed in the approved environment.
  • No CUDA, TensorRT, GPU, Kubernetes, distributed coordination, external traffic, uptime, or production scale was tested.
  • Docker files exist, but the local Docker daemon was unavailable for runtime verification.
  • The reference HTTP server still needs authentication, TLS, tenant isolation, durable control-plane state, per-model quotas, and circuit breakers before internet exposure.

10 / What I learned

Performance engineering is an exercise in precise comparison.

The most useful optimization was not a new backend; it was making the scheduler’s work visible and comparing one controlled variable at a time. I also learned that cancellation, overload, and cache identity are part of the serving result—not secondary polish.

The next meaningful step is not a larger headline number. It is running the same discipline against a real model backend and production-shaped traffic while adding authentication, tenancy, durable registry state, and distributed admission.

01 / Problem and motivation

An agent failure is hard to fix when the path disappears.

End-task success alone cannot explain whether an agent chose the right tool, sent valid arguments, followed the required order, recovered from a transient failure, refused without evidence, or trusted malicious tool output. If the tool behavior or evaluation conditions shift between runs, the failure becomes difficult to reproduce.

Engineering question: can a local deterministic harness preserve enough trajectory evidence to replay failures, compare strategies, and fail a regression check without depending on a paid model provider or nondeterministic judge?

02 / Project scope

Evaluation is the product, not a wrapper around a chatbot.

TraceLab AI evaluates two implemented deterministic strategies against a versioned benchmark and controlled corpus. It records tool calls and trace steps, persists runs to SQLite, exports JSON and Markdown reports, and exposes asynchronous jobs, cancellation, health, readiness, metrics, and a local dashboard.

  • 120 cases: ten in each of 12 categories.
  • Local calculator, date, extraction, retrieval, flaky-retrieval, and untrusted-retrieval tools.
  • Exact final-output, structured-output, tool-name, argument, order, recovery, grounding, citation, refusal, security, latency, token, and throughput metrics.
  • Searchable run history, trace replay, and regression comparison with nonzero exit on configured quality drops.

03 / My contribution

I implemented the evaluator from case file to regression gate.

I built the benchmark generator, direct and planner/executor strategies, isolated tool registry, bounded asynchronous runner, trajectory scorer, SQLite migrations and persistence layer, exports, HTTP job surface, cancellation path, rate limits, metrics, dashboard, comparison command, and tests.

The saved benchmark is not presented as a general leaderboard. Its job is narrower and more practical: make defined workflow behavior reproducible enough to support debugging and CI decisions.

04 / Architecture

One case, one isolated world, one complete trace.

05 / Important engineering decisions

Determinism is a debugging feature.

Use explicit expectations instead of an LLM judge

Exact outcomes and structured trajectory requirements remove provider cost, judge nondeterminism, and judge failure modes from the verified core.

Build a fresh tool registry for every case

Case isolation prevents state from leaking across runs and makes retry or recovery behavior repeatable.

Store trace boundaries, not just final scores

Runs, cases, steps, tool calls, arguments, outputs, errors, attempts, durations, and metrics stay queryable for replay.

Keep the core dependency-light

SQLite and the Python standard library make a clean local run possible without a database service, provider key, or paid API.

Treat tool output as untrusted data

The verified strategy accepts only the expected value line from the controlled untrusted-output path instead of executing embedded instructions.

06 / Technical challenges

Evaluation has its own reliability failure modes.

  • Bounded concurrency: a semaphore limits independent cases while asyncio.wait_for enforces a two-second case timeout.
  • Cancellation: a cancellation event is checked before admission and during retry; the HTTP API returns a job token and exposes a cancel endpoint.
  • Failure isolation: an exception becomes a case-local error rather than terminating the full suite.
  • Trace integrity: a versioned benchmark and suite content hash help detect changed evaluation inputs.
  • Security cases: prompt-injection and malicious tool-output cases require the agent to treat retrieved text as data, not instructions.

On the saved benchmark, the planner/executor also reached 100% for tool selection, arguments, trajectory validity, transient-failure recovery, missing-evidence refusal, prompt-injection resistance, and citation correctness.

Qualification: these results prove the behavior of two implemented deterministic strategies against an authored local suite. They do not measure a hosted foundation model, arbitrary tools, general intelligence, or production security.

09 / Limitations

A repeatable suite can still be narrow.

  • No LLM judge is used, so semantic equivalence beyond explicit expectations is not scored.
  • Provider adapters are intentionally absent from the verified core.
  • The benchmark is authored for regression testing, not a universal agent leaderboard.
  • SQLite, in-process rate limits, and the local dashboard are not a multi-tenant production architecture.
  • Authentication, TLS, authorization, encrypted persistence, distributed workers, and durable rate limits remain deployment responsibilities.
  • OpenTelemetry-compatible trace concepts are used, but the OpenTelemetry SDK/exporter is not installed and is not claimed.

10 / What I learned

Saved failures make evaluation useful between demos.

The most valuable output is not the 100% figure; it is a structured record that explains why a case passed or failed and can be compared after a change. This project reinforced that evaluation infrastructure needs timeouts, cancellation, isolation, versioning, and threat boundaries just like serving infrastructure.

A next iteration should preserve the deterministic core while adding provider adapters behind recorded fixtures, stronger artifact hashing, structured-output schemas, authentication, and a production-safe UI.
